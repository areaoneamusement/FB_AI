# CR-0003: Only factual assertions are claims, and Model B critiques in batches

- **Status:** Proposed
- **Spec:** `fb-ai`
- **Affected tasks:** `5.1`, `5.2`
- **Requirements:** 5.1, 5.2, 5.8
- **Properties:** 6

## Reason

Two live cycles reached verification with working sources and working models,
and neither could produce an article. The reports:

```
kiểm chứng chặn: 1
  13 claim không đạt, ví dụ Unsupported: The research does not provide a
  specific instruction to read the repo for setup; this is editorial advice.

kiểm chứng chặn: 1
  15 claim không đạt, ví dụ Unsupported: Đây là các hashtag, không phải thông
  tin từ research.

kiểm chứng chặn (có thể thử lại): 1
  ModelB ModelUnresponsive: Model B không trả phán quyết cho 65/98 claim
```

Both are defects in this implementation, not in the models. Model B judged
correctly in every case quoted above.

### 1. Every sentence is treated as a factual claim

Property 6 reads "Every **factual** claim in every format has exactly one
finding". `extractClaims` splits every field of the draft on sentence
terminators and calls each span a claim, with no notion of whether the span
asserts anything.

A published draft necessarily contains spans that assert nothing and therefore
can never be grounded in research:

- **Hashtags.** `#AI #LLM #TrungCahaAI` is a distribution tag, not a statement
  about the world. Model B says so, in as many words, and the draft is blocked.
- **Image suggestions.** `guide[0].imageSuggestions[0].description` is art
  direction for whoever produces the image. It is an instruction, not an
  assertion to a reader.

Because a single non-Pass finding blocks the revision, a draft containing either
of these can never be approved. The pipeline is structurally unable to deliver
its own output.

### 2. One critique call must cover an unbounded number of claims

A draft produced 98 claims. Model B answered 33 of them and the adapter
correctly reported incomplete coverage, which the engine correctly treated as a
retryable dependency failure. Retrying does not help: the request is the same
size every time.

Claim count grows with draft length, and the response has to carry one object
per claim. Nothing bounds either.

## Change

### Claims

A span is a claim only if it can assert something. Two exclusions, both
structural — neither depends on reading the text's meaning:

1. Spans whose every whitespace-separated token begins with `#`.
2. Any span under an `imageSuggestions[...]` path.

Headings, body prose, the Facebook post and the video script stay in scope in
full. A heading can carry a fabricated statistic, so it is still verified.

**What this deliberately does not change:** an editorial or exhortative sentence
in prose — "Hãy đọc repo để biết cách cài đặt" — remains a claim and still
blocks when Model B finds no support for it. Detecting mood or intent in code is
unreliable, and being wrong in that direction lets an invented statement through
unchecked. The generation prompt is tightened instead, to stop Model A writing
un-sourced advice in the first place.

### Batching

`GeminiModelBClient.critique` splits claims into batches of at most
`MAX_CLAIMS_PER_CRITIQUE` and merges the findings. Coverage is still checked
across the whole set, so a batch that goes unanswered is still a dependency
failure. This bounds the size of any single response without weakening the
coverage guarantee.

## Impact on properties

Property 6 is unchanged in substance: every claim still receives exactly one
finding, and a Contradiction or Unsupported finding still blocks. What changes
is which spans are claims — narrowed to those that can assert something, which
is what "factual claim" already said.
