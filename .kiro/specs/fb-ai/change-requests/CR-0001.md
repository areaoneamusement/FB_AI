# CR-0001: Realign task 2.1 port interfaces with the design

- **Status:** Approved
- **Approval:** Approved by user
- **Spec:** `fb-ai`
- **Affected task:** `2.1 Define port interfaces`
- **Requirements:** 1.1, 5.1, 8.6

## Reason

Task 2.1 is not implementable as written without contradicting the authoritative design:

1. It asks the repository to store a `Stage` with topics, drafts, research results, verification reports, and compliance results. The design instead makes `PipelineRun` the sole owner of mutable workflow state; artifacts are immutable and linked through transitions.
2. It specifies `OutputPort.deliver(draft, platform, item)`, while the design requires delivery of an already rendered and approved artifact through `DeliveryCommand`, returning `DeliveryOutcome`.
3. The design requires independent Model A and Model B adapters plus versioned model and prompt provenance, which the current task text does not state.

Implementing the current task literally would duplicate mutable state and weaken revision, approval, hash, and idempotency guarantees.

## Requested change

Replace task 2.1 with the following scope:

- Define `SourceFetcher` with `fetch(source, cursor, signal)` and `isAllowed(source)` using `FetchPage` and `SourcePermission`.
- Define typed, independently injectable Model A generation and Model B critique ports. Requests and responses must retain provider, model, prompt, and configuration versions and accept cancellation/deadline signals.
- Define a persistence port for topics, research results, immutable draft revisions, verification reports, platform artifacts, compliance results, approvals, pipeline runs, transitions, and delivery records.
- Keep current `WorkflowStage` and `WorkStatus` only on `PipelineRun`; do not duplicate mutable stage fields on domain artifacts.
- Require repository mutations that advance workflow state to support transactions, optimistic locking, and idempotency keys.
- Define `OutputPort.deliver(command: DeliveryCommand): Promise<DeliveryOutcome>` so output consumes an approved artifact and its exact hash rather than re-rendering a mutable draft.

## Acceptance criteria

1. Port definitions compile in strict TypeScript without concrete provider, database, or exporter dependencies.
2. `SourceFetcher` supports permission checks, durable cursors, cancellation, and paged fetch results.
3. Model generation and critique are independently replaceable and expose reproducibility metadata.
4. `PipelineRun` is the only canonical holder of mutable workflow stage/status.
5. Persistence contracts preserve immutable revision/artifact links and support atomic guarded transitions.
6. `OutputPort` accepts only an approval-bound artifact command and returns a typed delivery outcome.
7. Adapter fakes in task 2.2 can implement the ports without external I/O.

## Impact

This change realigns task 2.1 with the design's state ownership, immutable revision, exact-artifact approval, and delivery idempotency rules. No runtime behavior or source code is changed by this request.
